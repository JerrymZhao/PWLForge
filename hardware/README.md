# Hardware templates

The hardware is organized by numeric representation, not by function:

```text
rtl/fixed16/  shared fixed-point template for one 16-bit word per value
rtl/fixed32/  shared fixed-point template for two 16-bit words per value
rtl/fp16/     shared FP16 template and floating-point operation wrappers
rtl/fp32/     shared FP32 template and floating-point operation wrappers
constraints/  optional XDC timing setups
vivado/       synthesis helpers and floating-point IP creation Tcl
```

An `examples/<function>/<format>/data/` directory supplies the five memory
files and `pwl_config.vh` for a particular function.  The RTL is deliberately
not copied into every function directory.  The four fixed16 examples were
generated by the current release from the selected configurations:

| Function | Range | Selected configuration |
| --- | --- | --- |
| `tanh(x)` | `[0, 1]` | `Fixed2_14_Fixed2_14` |
| GELU | `[-3, 3]` | `Fixed4_12_Fixed3_13` |
| SiLU | `[-5, 5]` | `Fixed5_11_Fixed3_13` |
| HSwish | `[-3, 3]` | `Fixed4_12_Fixed3_13` |

The template uses relative paths such as `data/group_info.mem`.  In Vivado,
run from the selected example directory, or otherwise make its `data/`
directory the working directory and add the corresponding RTL directory to
the include/source search path.

## Fixed point

`fixed16` and `fixed32` share the same two-level HLUT datapath.  They are kept
as separate templates because the packed ROM layout differs: fixed16 stores
one 16-bit word per value, while fixed32 stores two little-endian 16-bit words
per value.  The included fixed16 examples are current generator outputs.
Generate a fixed32 configuration before pairing data with `rtl/fixed32`.

## Floating point

The FP16 and FP32 templates use AMD/Xilinx Floating-Point IP for add,
multiply, and comparisons.  Vendor-generated IP, netlists, Vivado projects,
and caches are intentionally not versioned.  Create compatible local IP with:

```sh
vivado -mode batch -source hardware/vivado/ip/create_fp_ips.tcl
```

Then add the generated IP plus the RTL wrapper sources to your project.  The
two included floating-point data examples are retained as historical template
inputs (HSwish FP16 and SiLU FP32); they are not regenerated by the current
fixed-point export path.  The IP configuration and latency must stay aligned
with `fp_config.vh` and the wrapper latency constants.

## Timing constraints

`core_clk_{200,300,400,500}mhz.xdc` constrain only internal
register-to-register paths. `clk_{200,300,400,500}mhz.xdc` additionally apply
illustrative AXI-stream I/O delays.  They support an optional timing sweep;
they are not a claim that all templates meet those frequencies. The paper's
100 MHz setting is a demonstration point; tested ZCU102 core-only runs met
400 MHz for Fixed16 and 300 MHz for Fixed32.

To implement one shared fixed16 template/example pair, use the parameterized
entry point:

```sh
VIVADO_EXAMPLE=examples/tanh/fixed16 \
VIVADO_TEMPLATE=hardware/rtl/fixed16 \
VIVADO_XDC=hardware/constraints/core_clk_200mhz.xdc \
vivado -mode batch -source hardware/vivado/run_fixed_core_timing.tcl
```

`vivado/run_fixed_core_timing_sweep.tcl` is retained only as a reference for
the legacy design-per-function sweep layout.
